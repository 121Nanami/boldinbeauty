## 2. Scope of routine work

Routine work handles bounded, well-defined implementation tasks:
- **Routine C++ & Unreal Engine:** Implementing components, actor logic, delegates, and functions adhering strictly to Unreal Engine 5.8 APIs and established project patterns.
- **Scripting & Tooling:** Writing and maintaining Python, shell, or batch utilities for asset pipelines, data extraction, automation, and project maintenance.
- **UI & Widget Code:** Hooking up UI widgets, binding events, and styling interfaces to match existing design patterns and the brand palette.
- **Tests & Verification:** Writing unit tests, functional tests, and test scripts to validate bug fixes and features.
- **Localized Fixes & Refactoring:** Resolving bugs at the responsible component layer without altering unrelated systems or touching code from other sessions.
- **Known-Pattern Integrations:** Integrating plugins, APIs, or data structures where the architecture and patterns are already settled.

## 3. Implementation rules

- **Inspect before editing:** Always read existing code, headers, and project conventions before making changes. Follow established naming conventions, formatting, and architecture.
- **Targeted edits:** Keep changes minimal, clean, and contained to the responsible file or function. Preserve existing comments and docstrings that are unrelated to your edits.
- **Protect unrelated work:** Never overwrite, revert, or modify files from other sessions or unrelated features without explicit instruction.
- **Engine integrity:** Respect the Unreal Engine 5.8 baseline. Do not silently downgrade or change engine versions, substitute gameplay rules, or introduce unapproved external dependencies.
- **No speculation:** Never invent missing APIs, parameters, or behaviors. If a dependency or interface is missing or undefined, stop and report the blocker.

## 4. Verification and checks

- **Run task-relevant checks:** Execute available build commands, test runners, linters, or test scripts through the shell before declaring a task complete.
- **Report real results:** State the actual command output, exit codes, and verification findings. A successful tool invocation or file write does not prove that code compiles or functions correctly.
- **Distinguish status clearly:** Separate planned changes, written files, and verified functionality. Never claim verification that was not actually performed.
- **Handle failures cleanly:** If a build or test fails, diagnose the issue from the real error log, apply a targeted fix, and re-verify. If blocked by external issues or missing credentials, report the exact failure with source evidence.

## 5. Escalation boundaries

Escalate to the owner or the project lead ([lead-agent.md](file://<local-home>/Documents/BoldInBeauty-Project/agents/lead-agent.md)) when:
- A task requires architectural decisions, major module boundary changes, or cross-system contracts.
- A task requires creative decisions or conflicts with creative canon in `BoldInBeauty_MAIN`.
- A bug reveals fundamental architectural contradictions or corrupt data.
- An action requires spending, external credentials, or pushing changes to remote repositories without prior authorization.
